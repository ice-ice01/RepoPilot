研伴 RepoPilot / Architecture Guide

GitHub 协作数据是怎样进入系统的？

把它想成一个 Spring Boot 数据同步模块：多个入口只负责“发起同步”，真正的 GitHub REST 拉取、字段映射和数据库 upsert 都集中在一个 Service 中。

Spring 对照接口与表跟踪一条 Issue如何进入 AI容易误解的边界源码导航

01 / 一次真实同步的调用顺序

以下为教学演示，不执行真实请求。入口切换会改变调用顺序；源码分析与 RAG 不是协作同步的必经步骤。

步骤 1 / 6
    协作数据准备发起本次同步
    源码 checkout连接或手动刷新后单独调度
    RAG / 关系图谱本次演示不更新；它们有独立入口

    逐步解释

    关键结论：Webhook 只通知“有变化”，系统随后仍通过 GitHub REST API 重新拉取；它不是消息正文入库接口。

    连接仓库

    POST /api/repos/connect
    1. 先验证仓库可访问，并保存 repositories 配置。
    2. 等待协作数据首次同步，默认每类接口仅请求第一页 5 项。
    3. 响应后执行源码分析；演示模式不走真实协作同步。

    手动刷新

    POST /api/repos/{repo_id}/sync
    1. Controller 根据 UUID 找到 Repository。
    2. 直接 await sync_repository()，所以响应前协作表已提交。
    3. 响应后再执行源码 checkout/分析。

    Webhook

    POST /api/webhooks/github
    1. 有 secret 时校验 X-Hub-Signature-256，未配置则跳过。
    2. 按 payload.repository.full_name 定位已连接仓库。
    3. 只对 issues / pull_request / workflow_run / push / check_suite / check_run 调度协作同步，三个同步开关默认全开。
    4. 不会在这里调度源码 checkout 或 RAG 索引。响应 accepted 表示已调度，不是已完成。

    定时同步

    periodic_repo_sync_loop()
    1. 应用启动时创建任务，先等待 5 秒。
    2. 遍历 github / github_compatible 仓库，逐个等待协作同步。
    3. 一轮完成后默认等待 300 秒，最低 30 秒；不是严格每 300 秒开始新一轮。
    4. 不调度源码或 RAG；单仓库异常记日志后继续。

    // Java 直觉版（仅用于理解，不是项目源码）
@PostMapping("/api/repos/{id}/sync")
public SyncResult sync(UUID id) {
    Repository repo = repositoryRepo.findById(id).orElseThrow();
    List<IssueDto> issues = githubClient.listIssues(repo.owner(), repo.name());
    issues.forEach(issue -> issueRepo.upsert(repo.getId(), issue));
    return new SyncResult("completed");
}

    先掌握 6 个 Python 表达方式，就能读这段业务代码

    Python 写法Java 直觉注意点
    async def f(...) -> T声明一个可等待、返回 T 的方法async 本身不意味着另起线程，也不意味着响应已经返回。
    await f(...)“等这个调用完成，拿结果再继续”可以把控制权交还事件循环，但当前调用链仍在等待。
    item.get("body")Map.get("body")取不到是 None，近似 null；get("state", "open") 提供缺失键的默认值。
    x if flag else yflag ? x : y三元表达式只是顺序与 Java 不同。
    [x.get("name") for x in labels]labels.stream().map(...).toList()列表推导式，把远端对象列表转换为字段列表。
    with / finallytry-with-resources / finally用于关闭 HTTP 客户端或数据库 Session。

    db.query(...).filter(...).one_or_none() 可以按“查一条，没有则 null”理解；db.add(entity) 把新增实体加入 Session。已有实体修改字段后，SQLAlchemy 会在 flush / commit 时写回，不需要每个字段调用 update。

    03 / GitHub 哪些接口，对应本地哪些表？

    sync_repository() 按 Issue → PR → CI 的顺序处理，各分支由请求 DTO 的开关控制。当前实现不是同时发出全部请求，也不是 LangChain 自动抓取。

    数据与 GitHub REST 路径封装文件入库内容
    仓库配置
    GET /repos/{owner}/{repo}    		services/github/client.py
    get_repo()    		repositories：仓库全名、描述、默认分支、clone URL、加密 token、API base URL。
    Issue
    GET /repos/{owner}/{repo}/issues    		services/github/issues.py
    list_issues()    		issues：标题、正文、状态、标签、作者、负责人、时间。过滤返回项中的 PR。
    PR
    GET /repos/{owner}/{repo}/pulls    		services/github/pull_requests.pypull_requests：标题、正文、状态、作者、base / head 分支、合并与更新时间。
    PR 文件
    GET .../pulls/{number}/files    		list_pull_request_files()pr_files：文件名、修改类型、增删行数、patch。
    代码行 Review 评论
    GET .../pulls/{number}/comments    		list_pull_request_review_comments()pr_review_comments：正文、路径、行号、作者、时间。不是 Issue 的普通讨论评论。
    CI 运行 / jobs / 日志
    GET .../actions/runs
    GET .../runs/{id}/jobs
    GET .../runs/{id}/logs    		services/github/actions.pyworkflow_runs：状态、结论、URL、jobs / steps。结论为 failure 时下载 ZIP 日志，转换成文本，最多 80,000 字符。

    GitHubClient 用 httpx 发请求，统一设置 Accept、API 版本和 Bearer token。token 优先用仓库配置，未提供时客户端可回退到全局 GITHUB_TOKEN。仓库 token 经 core/security.py 加密保存，使用时再解密；这并不是 OAuth 回调或 GitHub App 安装流程。

    真正的关键代码，删减展示

    remote_issues = await list_issues(repo.owner, repo.name, ...)
for item in remote_issues:
    issue = db.query(Issue).filter(
        Issue.repo_id == repo.id,
        Issue.github_issue_id == item.get("id")
    ).one_or_none()
    if issue is None:
        issue = Issue(repo_id=repo.id, github_issue_id=item.get("id"), ...)
        db.add(issue)
    issue.title = item.get("title") or issue.title
    issue.body = item.get("body")
    issue.labels = [label.get("name") for label in item.get("labels", [])
                    if label.get("name")]
    synced["issues"] += 1
...
db.flush()
db.commit()

    第一次同步：查不到记录 → 新建实体。第二次同步：用 repo_id + github_issue_id 找到原记录 → 更新字段。这是代码层面的“先查后更新或新增”，不是数据库原生的 ON CONFLICT。number=42 是仓库内展示编号，远端 id=7800 用来匹配，本地 UUID 用于系统内部关联。

    flush() 近似 JPA 的 flush：SQL 发往当前事务，但不等于提交。commit() 才确认当前数据库事务；并且仓库配置在连接入口已经单独 commit，所以“仓库连接配置 + 协作同步”也不是一个总事务。

    05 / 数据入库后，如何被页面和 AI 使用？

    通道 A：按 ID / 状态查询实时业务事实

    api/routes/issues.py、pull_requests.py、ci.py 读取本地表。聊天中的 chat.py → _repo_payload() 也读这些表。分析入口把实体转成字典，交给 IssueAgent、PRReviewAgent、CIDebugAgent；这些分析还可以结合知识检索和源码证据。入库并不等于立刻调用 AI 分析。

    通道 B：从协作文本建立 RAG 检索资料

    POST /api/rag/{repo_id}/reindex
  → api/routes/rag.py : reindex_rag()
  → services/rag/qa.py : reindex_documents()
  → services/rag/indexing.py : index_repository_documents()
  → PostgreSQL documents（正文 + 来源元数据）
  → embeddings.py（把文本变成向量）
  → vector_store.py（写入 Milvus）

    你可以直接对应到 Spring AI 的 ETL：业务表 → Document → EmbeddingModel → VectorStore。Issue 使用标题 + 正文；PR 使用标题 + 正文 + Review 评论，文件名放入元数据，不把全部 patch 拼进此 PR 文档；CI 只选“失败且有日志”的运行，先脱敏，再最多切成 6 个 8,000 字符块。

    问答阶段相反：answer_question() → retrieve_knowledge() 检索相关证据（可配置向量 / 全文 / 混合检索）→ 根据证据门控决定是否回答 → 有需要且模型可用时调用 LLMClient.chat_text()。可以类比 Spring AI 中“Retrieval Augmentation 后交给 ChatClient”，但不能把两套 API 当作完全一样的实现。

    只按“同步”会更新 Issue / PR / CI 表，不会自动刷新 documents 或 Milvus。刚同步的问题可以出现在列表里，却暂时不能被语义搜索命中。需要另外执行 reindex；PostgreSQL 与 Milvus 也不是跨系统原子事务。

    通道 C：源码与关系图谱，不要混成一个概念

    code_analysis.py 准备工作树，扫描符号与关系，写入 code_symbols / code_relations。托管仓库首次 shallow clone，后续 fetch / checkout / pull；用户选择的本地工作树直接读取，不在这里自动拉取。默认目录在后端的 .data/repos/{repo_id}-{owner}__{repo}，用户可指定位置。

    当前源码不作为 code_file RAG 文档向量化，相关旧文档会被清理；聊天通过工作区文件读取 / 搜索获得源码证据。README、设计文档等项目资料有独立的 project_indexing.py 扫描入口，不能理解成“连接仓库后所有源码全部灌进向量库”。

    另一个 knowledge_graph.py 从本地协作表、文件和文档推导关系，例如 PR 关联 Issue、PR 修改文件，保存 knowledge_graph_edges。显式入口是 POST /api/repos/{repo_id}/knowledge/graph/rebuild，项目资料扫描也可触发；图谱查询在边数为 0 时会懒构建，不代表已有图谱每次同步都自动刷新。

    06 / 读源码时最容易误解的边界

    它是不是把 GitHub 历史协作数据全部导入？

    不是。当前 REST 封装只请求第一页，没有处理分页 Link / page 的循环。首次连接的 DTO 默认 initial_sync_limit=5，手动刷新前端传 50，Webhook / 定时默认 50；PR 文件、评论、jobs 每页 100。Issue 接口过滤 PR 后，实际条数还可能更少。没有基于 last_sync_at 的增量游标，也没有完整删除对账。

    看到 synced=10，就是新增了 10 条吗？

    不是，计数是本次处理的条数。已有记录被更新也会累加。status=completed 也不保证每个子接口都成功：Issue / PR 主列表的 HTTP 错误会中断；CI 主列表错误可被处理为空列表，PR 子接口错误可被处理为空集合。因此只看计数或 last_sync_at 不足以确认全部历史已导入。

    PR 文件和评论，也像主记录一样逐条 upsert 吗？

    不是。它们先删除已有集合，再拉取并重插。当子接口返回 HTTP 错误时，本次集合会是空的，后续 commit 可能清掉原集合。当前实现行为需要与“保留旧数据”的期望区分。

    Webhook 的 push 事件会同时更新代码吗？

    这个 Webhook 入口只调用 sync_repository_by_id() 同步协作数据，不调度代码分析。连接或手动刷新才会额外加入源码分析后台任务；定时循环同样只同步协作数据。

    BackgroundTasks 能像 RabbitMQ 一样保证任务不丢吗？

    不能。任务运行在应用进程内、HTTP 响应发送之后，当前代码没有持久队列、消费确认或按事件去重机制。Webhook 返回 accepted=True / sync_scheduled 只是已调度。生产环境还应配置 GITHUB_WEBHOOK_SECRET，否则当前实现跳过签名校验。

    Demo / fallback “连接成功”意味着远端数据已经导入吗？

    不意味着。显式 demo 只创建本地仓库记录；GitHub 验证失败、无 token 且允许 demo fallback 时可进入本地缓存模式，协作同步被跳过。fallback 分支可能仍调度源码分析，请看响应里的 demo_mode、sync_status 和 synced，而不只看 connected。

    我必须先学 LangChain 才能理解这里吗？

    不需要。项目依赖列表确实包含 LangChain / LangGraph，但本次 GitHub 采集链路是 FastAPI + httpx + SQLAlchemy；相关 RAG 文档转换、Milvus 封装和 LLMClient 也可按普通业务服务阅读。先把 Controller → Service → HTTP 客户端 → Entity 理解清楚，再看 Agent 编排。
