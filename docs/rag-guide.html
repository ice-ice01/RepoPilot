研伴 RepoPilot 的 RAG，实际怎样运行？

可以把它理解成一套手写的 Spring 服务：先把项目知识整理成 Document，再做向量与关键词检索，最后把证据放进提示词回答。核心检索流程并不是 LangChain 自动提供的。

依据当前项目源码整理。示例不是你数据库里的真实数据；默认参数也不代表当前运行配置。此页可离线打开，配套示例数据在同目录的 rag-chunk-examples.js。

01 · 先分清：存知识、找知识、用知识

写入：原始资料 → 文本提取 → 结构切片 → Embedding → SQL + Milvus
检索：用户问题 → 查询向量 + 关键词 → 候选 → 重排 → 证据片段
回答：问题 + 证据片段 → 提示词 → 生成模型 → 带引用的回答

Embedding 类似把文本变成固定长度的 float[]，相近含义尽量靠近；它不是生成答案的模型。RAG 也不是训练模型，只是给本次请求补充外部资料。

关系库：正文与业务事实

documents 保存正文、标题、来源和 metadata；knowledge_source_documents 保存上传文件的状态与统计。项目默认 PostgreSQL，测试等场景也能用 SQLite。

⇄
Milvus：相似度检索

保存向量、仓库标识、来源和文本副本；用 COSINE + AUTOINDEX。Document 实体本身没有 embedding 字段。

数据库中存在 Document，不等于已经进入 Milvus，也不等于允许进入 RAG。SQL 和 Milvus 没有跨库原子事务，SQL 回滚不能自动撤销向量写入。

02 · 三条流程，不能混为一谈

“上传文档”“独立 RAG 问答”“聊天 Agent 搜索工具”共享部分函数，但编排不同。下方每一步都对应真实代码；动画只演示调用顺序，不发请求、不写数据库。

还有一条批量重建路径

POST /api/rag/{repo_id}/reindex → qa.reindex_documents：从本地业务表刷新 Issue、PR、失败 CI 文档，选出允许 RAG 的 Document，分批算向量，删除该仓库旧 Milvus 数据并重新写入。

GitHub 同步负责把远端资料写进业务表，不自动执行 RAG 重建。重建复用已有上传 / 项目文档切片，不会重新读取原文件或按新参数切片。新上传管理的 retry 才会重新解析、切片；项目文档要重新扫描。

03 · 究竟哪些数据会写入 RAG？

source_policy.py 的白名单只有下面六类。“允许向量化”是资格，是否已经写入还取决于索引入口与处理状态。

source_type实际正文构建 / 写入时机切片方式
issueIssue 标题 + body；不包含 Issue 评论reindex 从本地 Issue 表构建整条作为一个 Document
pull_request标题 + body + Review 评论的路径、行、作者与正文。改动文件名放 metadata，不把 patch / diff 正文拼进来reindex 从本地 PR / Review 表构建整条作为一个 Document
workflow_run失败 CI 的非空日志；先专门脱敏，再截断reindex 从本地 WorkflowRun 表构建最多 48,000 字符，8,000 字符一片，最多 6 片，无 overlap；再附名称
project_doc仓库中指定的 Markdown：README、ARCHITECTURE、CONTRIBUTING、docs/、ADR、变更记录、Issue 模板等项目扫描先写 SQL / Evidence，reindex 才同步 Milvus结构切片，固定 1800 / 180 字符
knowledge_file用户上传文件提取后的文本新上传后台处理；旧上传在请求内处理；均写 SQL + Milvus按格式；新入口用仓库配置，旧入口固定 1800 / 180
memory_note人工新增笔记，或用户批准的长期记忆候选创建笔记 / 批准候选时写入全文一条；不是所有聊天内容自动入库

这些不走 RAG 向量库

project_overview、project_manifest、团队成员、周报、会话 / 对话 / 线程记忆等走业务表、记忆接口或工作区工具直接查询。code_file 不在白名单，向量库写入还会明确拒绝它；源码主要走工作区实时搜索。

所以不能因为项目有 chunk_code_text、chunk_pr_files 函数，就认为源码或 PR diff 正在进入当前 RAG 主链路。KnowledgeSourceDocument.source_type = upload_file 是上传管理记录；检索用的 Document 类型是 knowledge_file。

项目扫描的筛选限制

先按路径 / 文件类型分类，再应用 .devflow/index.yml 的 auto / allowlist 和 include / exclude；include 不能把任意源码改成 project_doc。跳过秘密文件、生成目录等；最多发现 500 个文件，读取单个文本最多 400,000 字节，检查 NUL 并尝试字符编码。项目概况和依赖清单即使以 Document 存储，仍为 direct。

04 · 当前“清洗”，实际做了什么？

这里的主策略是格式提取 + 基础规范化 + 安全 / 资源限制，不是一套完整的智能文档清洗流水线。核心函数是 extract_document_text 和 chunk_document。

输入代码实际处理未覆盖的能力 / 注意点
TXT / MD / JSON / CSV 等文本拒绝开头 8192 字节中的 NUL；尝试 utf-8-sig → utf-8 → gb18030 → latin-1；切片时 CRLF / CR 转 LF，去边缘空白编码兜底不保证准确；不是全文去噪或秘密扫描
PDFpypdf 读取已有文本层，各页 strip；加入 <!-- page: N -->，空文本页略过没有 OCR；图片扫描 PDF 可能无法索引。没有通用页眉页脚清除或阅读顺序修复
DOCXpython-docx 按正文顺序提取：标题变 Markdown #；列表变简单标记；表格变管道文本，首行当表头不恢复 Word 真实分页，不读图片文字或页眉页脚；复杂排版仅简化为文本
失败 CI 日志专门用正则遮蔽私钥、GitHub / AWS token、JWT、Bearer、add-mask 及 secret / token / password 等赋值是 CI 专用逻辑，不能推断上传文档也有相同脱敏

防止文件处理失控

上传上限 12 MiB；提取文本最多 400 万字符；PDF 最多 500 页；DOCX 最多 10,000 个 ZIP 条目、64 MiB 解压内容，拒绝加密条目；切片总量最多 5,000。

三种“去重”，不是一回事

新上传入口按仓库 + 文件字节 SHA256 查重（排除 failed 记录）；已有切片重试按来源替换；查询时再用文本指纹 / Jaccard 做近重复候选去重。没有全库语义文档去重。

当前没有统一的页眉页脚去除、模板噪声过滤、图片 OCR、上传文件全面脱敏，或基于 LLM 的语义切片。不要把提取 / 切片等同于已经“洗干净”。

05 · 切片是按字符 + 结构，不是按 token

max_chars / chunk_size 和 overlap / chunk_overlap 都是字符数。例如汉字通常算一个字符；与 Spring AI 的 token splitter 不能直接按相同数字比较。

入口size / overlap是否读仓库配置？
新 /api/rag 上传、retry配置初始默认 800 / 100是
旧 /api/repos/{id}/knowledge/upload固定 1800 / 180否
项目文档扫描固定 1800 / 180否
直接调用 chunk_document 未传参数函数默认 1600 / 160函数不负责查库
Issue / PR / memory_note / CI见上面的来源表不是普通上传的切片路径

配置接口约束：size 200～4000，overlap 0～1000，且 overlap < size。当前运行值需看仓库配置，不能只看函数定义。

TXT / LOG：字符滑动窗口

_plain_chunks 从 cursor 取最多 max_chars 字符；未到末尾时，在窗口后半段找最后的空行 / 换行，尽量在此结束，否则硬切。下一窗从 max(cursor + 1, end - overlap) 开始，因此既带重叠又保证前进。去首尾空白后，实际重复正文可能少于 overlap。

MD / PDF / DOCX：先拆结构块，再装箱

_markdown_blocks 用标题栈维护 #～######，用出现次数区别同名章节；空行结束段落，代码围栏独立成块，PDF 页标记更新 page。_pack_blocks 只合并同一章节实例、同一页的块。达到容量就发出切片，再尝试带上前片尾部。

每片补上章节路径 / Page 前缀，前缀也算在字符预算里，正文存在时前缀最多 512 字符且不超过总预算三分之一。长段落先按中英文句末 / 换行拆，长句还超限才硬切。代码围栏超长时按行拆，补围栏；极长单行也硬切。围栏不进入 overlap；跨章节 / 页码不重叠。实际 overlap 受句 / 词边界和剩余容量影响，不保证精确等于目标值。

JSON / CSV：保留基本数据结构

JSON 用 json.loads 解析并美化；小文件整块；大文件按顶层键或数组项生成块，长值再拆。没有递归到任意深度的语义分割；拆后的块不保证都是合法 JSON。解析失败则回退为普通文本块再装箱。

CSV 用 csv.reader 解析，尽量按完整记录装箱，每片重复表头，重叠按整条记录选取，所以可能超出 overlap 目标。超长表头单独分片；巨型行按字符分片并加 row_part 等信息。含单元格内换行时，精确物理行定位可能为空，不应把 row_start 当绝对文件行号。

06 · 检索不是“查一次向量库就结束”

      
底层入口 search_similar_documents 支持 vector / fulltext / hybrid，其中 fulltext 是关键词模式。先限定仓库、RAG 来源白名单与 metadata 条件；Milvus 的仓库 / 来源条件在查询时使用，其他 metadata 条件多在向量召回后过滤。

      

        
向量路：含义接近
问题用与入库相同 provider / model / dimensions 的模型编码，Milvus 按 COSINE 找候选。默认设置为本地 Qwen/Qwen3-Embedding-0.6B、1024 维；本地查询编码用 query prompt。也有兼容 API、DashScope、显式 deterministic 等实现。
向量空间合同必须一致；不会静默补零 / 截短，也不会在模型加载失败后偷偷切换成 deterministic。默认配置不是运行实况。

        
关键词路：名称匹配
从 SQL 读取当前仓库的 Document，在 Python 内存里计算加权 BM25，K1=1.5、B=0.75。标题权重 4、路径 3、符号 4.5、标签 2.5、正文 1。英文取词 / 标识符，中文取单字和相邻双字。
它不是 Elasticsearch、数据库全文索引或现成 LangChain BM25Retriever。分批读库，但语料统计仍在内存累积。

      

      
合并、去重、限制占位

      
各路分数先除以本路最大值做相对归一化，再按 chunk_id（没有则按文档 id）合并。hybrid 使用下面的加权公式，不是 RRF，也不是相关性的概率。同 parent / 来源内，正文指纹或词集合 Jaccard ≥ 0.9 视为近重复；每个 parent 最多保留 2 条候选，防止一个长章节霸占结果。

滑块表示已归一化的候选分数；设为 0 表示该路无有效命中。只计算 hybrid 融合，不模拟后续重排、门控或最终阈值。

完整编排增加的步骤

      
retrieve_knowledge 为重排先取 20～100 条候选：min(max(K × (重排开启 ? 8 : 2), 20), 100)。底层每路再取 min(max(limit × 8, 40), 200)，所以 TopK 不等于最初召回数。

      
开启重排时优先用配置的 Qwen API，未配置或失败则用本地启发式；本地规则看关键词覆盖、标题 / 路径匹配、新鲜度等，默认重点重排前 24 条。然后截 TopK，再从 SQL 补同一 parent 的前后相邻各 1 片，并检查来源、仓库与存在的 branch / commit / version / checksum 等字段，避免混版本。补的是兄弟片段的上下文，不是加载全部父文档。

      
接着按最终 score 过滤，默认启用 0.8 阈值。这个分数可能已经被融合 / 重排改写，不等于原始 cosine=0.8。配置 TopK 初始值 3，而 ask/search 请求 schema 默认 5，会覆盖配置；最终限制在 1～20。

      
向量服务不可用，会怎样？
底层 hybrid 捕获 MilvusUnavailableError 后可以继续 BM25；纯 vector 抛错。但完整入口在底层召回前已计算查询向量，embedding 失败并不保证能自动降级为关键词搜索。这里也不是把所有服务异常都吞掉。

    


    

      
07 · 查到以后，怎样变成答案？

      
1
压缩证据，不是再次切片入库。从正文中抽取与问题相关的句子，最多约 4 句，每条最多约 260 token。总预算为 min(1800, max(520, K × 260))。中文按字符、英文约 4 字符一个 token 估算，并非精确模型 tokenizer。最终去掉内部 _raw_content。
context_compression.compress_retrieval_results

      
2
规则门控判断是否应该回答。没有证据、关键名称缺失等返回 insufficient_evidence；至少两条 score ≥ 0.6 的片段出现规则识别的正反标记冲突时返回 conflict；指代不明确时返回 ask_clarification；其余为 answer。不是另一个大模型在判卷，也不能保证识别所有自然语言矛盾。
answer_gate.evaluate_answer_gate

      
3
只把选中的片段放进提示词。qa 将编号片段放入 <knowledge>，要求只依据证据、引用 [n]，并把资料看作不可信输入，不能执行里面的指令。门控不允许 answer，就不调用生成模型。
qa.answer_question → _context_message → LLMClient

      
4
有条件的摘录兜底。生成未启用 / 缺少配置或模型返回空文本时，改为从来源摘出相关原句。这里没有捕获所有 chat API 异常，不能理解成“任何模型失败都能兜底”。search 与 retrieval-tests 只返回检索结果和诊断，不生成答案。
qa.extractive_answer

      
聊天 Agent 的 _semantic_search 直接调用底层 search_similar_documents，通常有本地重排与压缩，但没有上述完整服务的 Qwen 编排、相邻片扩展、配置阈值与规则门控。Agent 可以改写问题或再次调用工具，因此聊天效果不能直接等同于 /ask 测试结果。

      
存储副本有长度差异

      
Milvus 字段默认限制：标题 500 字节、正文 8192 个 UTF-8 字节、metadata 4096 字节，写入时可能裁剪。SQL 保留完整正文。因此没有普通切片的长 Issue / PR、CI 日志或笔记，向量检索得到的文本副本可能短于 SQL 关键词路。字符数与 UTF-8 字节数也不是一个单位。

    


    

      
08 · 用你熟悉的 Java / Spring AI 理解

      
本项目熟悉的对应物区别

        
FastAPI router / Depends(get_db)@RestController / 参数依赖注入入口是函数，不一定是一整个 Controller 类
SQLAlchemy Session / DocumentJPA EntityManager / Entity此处 Document 是数据库实体，不是 LangChain Document
extract_document_textDocumentReader返回字符串，结构定位后续生成
chunk_document自定义 DocumentTransformer / TextSplitter按字符和结构，不直接采用 token splitter
embed_knowledge_documents / queryEmbeddingModel入库与查询必须保持同一向量合同
upsert_milvus_documentsVectorStore.add(...) / upsert本项目手动管理 Milvus 与 SQL 双存储
retrieve_knowledge@Service 编排多个 Retriever / PostProcessorPython 自定义融合、重排、扩展、压缩与门控
qa._context_message + LLMClient检索增强 Advisor + ChatModel生成是独立步骤，不是向量模型在回答
ChatAgent 中 LangChain tools工具调用 / ToolCallback主要组织 Agent、消息与工具，不是 RAG 核心算法来源
BackgroundTasks / asyncio.to_thread进程内后台任务 / 线程池任务不是独立消息队列，不具备持久任务投递语义

      

      
读 Python 时，先认这几种写法就够了
def f(...):                 # 普通方法；缩进界定代码块
async def f(...): await g() # 异步方法；await 等待异步结果，不等于自动开启线程
list[dict[str, Any]]        # 类似 List<Map<String, Object>>
item.get("page")            # 类似 map.get("page")，缺少时返回 None
items[:top_k]               # 类似 subList(0, min(top_k, size))
[x for x in items if ...]   # 类似 stream().filter(...).toList()
{**old, "score": value}     # 浅拷贝 Map 后覆盖 score
@dataclass                  # 类似自动生成构造器的 DTO；不是数据库 Entity
return items, trace, ms     # 返回 tuple，可类比封装三个字段的 Java record

常见问题，先看哪里？

      
现象先检查

        
GitHub 同步了，RAG 仍没有资料同步只写业务表；是否执行 reindex？
项目扫描了，向量检索没有结果扫描只写 SQL / Evidence；是否 reindex？hybrid 的关键词路可能已经能搜到。
改了 chunk_size，片数没变参数只影响下一次新上传 / retry；reindex 不重新切片；旧上传与项目扫描另有固定值。
扫描 PDF 返回空内容是否只有图片？当前没有 OCR。
有候选，却最终无证据 / 不回答查看 trace.pipeline 的阶段数量、最终阈值、压缩预算及 answer_gate。
